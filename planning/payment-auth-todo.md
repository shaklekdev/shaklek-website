## Authentication

### Customer accounts — built 2026-08-16
- [x] **Checkout still stays fully guest by default** — no forced sign-up, matches dossier's low-friction positioning. Guests get a real confirmation email (see Payment section) with an offer to create a free account after paying, not before.
- [x] **`/sign-up` (public) is now separate from `/sign-in` (staff-only, see below).** The instance-wide Clerk allowlist that briefly restricted sign-up to only the two staff emails was disabled again (`PATCH /v1/instance/restrictions {"allowlist": false}`) once customer accounts became the goal — `/dashboard/*` staff access is unaffected either way, since that was always enforced separately by `STAFF_EMAILS` in `dashboard/layout.tsx`, not by the sign-up-level restriction.
- [x] **`/account`** — customer order history, protected by `proxy.ts` (any signed-in user, no staff allowlist). Matches orders to the signed-in Clerk user by email against `customers.email`, not a stored Clerk user id — so orders placed as a guest automatically appear once the customer signs up (or signs in, if they already had a staff/other account) with that same email. Verified end-to-end live: guest checkout with a real Stripe test payment → order confirmed + emailed → signed in with the same email → order appeared in `/account` correctly.
- [x] Header shows "Sign in" (signed out) or a `UserButton` (signed in) with a custom "My orders" → `/account` menu item, consolidated into the account dropdown rather than a separate nav link.
- [x] **Clerk's default avatar is an unstyleable remote image** (`img.clerk.com`, fixed purple gradient, not affected by the `appearance` prop since it's a raster image not a DOM element) — hidden via `.cl-avatarImage { display: none }` in `globals.css` so the avatar box's own background (themed brand-black via `appearance.elements.avatarBox` on `ClerkProvider`) shows through as a plain solid circle instead.
- [x] **Clerk**, chosen over Cognito and over Auth.js/NextAuth. Reasoning: Cognito is the "stays inside AWS" option but has real, well-known developer-experience friction for custom flows — not worth it for a solo maintainer. Auth.js is free and flexible but self-hosted: you own the session logic, the database adapter tables, and keeping it patched. Clerk is a fully managed service — prebuilt sign-in UI, session handling, and magic-link/social login all done for you — which means the least ongoing maintenance of the three, and its free tier (50,000 monthly retained users, corrected 2026-08-16) comfortably covers pilot scale. "Easiest" and "cheapest" point the same direction here, which is why it won over Auth.js despite Auth.js being nominally free.
- [ ] Magic link as the *only/primary* sign-in method — not enforced yet, email code + password + Google OAuth are all currently available since that's Clerk's default; deciding to narrow this is still open
- [ ] Saved measurements/preferences, the "digital wardrobe" retention feature (dossier §10), and Shaklek+ subscription state — `/account` currently only shows order history, nothing else yet
