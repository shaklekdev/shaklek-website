# RCA — the five bugs of 2026-08-26/27

**What happened:** five real defects were found and fixed across three commits
on the night of 2026-08-26/27. None moved money. Three touched customer body
measurements — PII under this project's own privacy policy. One disabled the
alarm that exists to catch every other silent failure. One made a working
security control unreachable in production while every console said it was
configured.

This file is the *why*, in the mould of `rca-2026-08-23.md`. That RCA's own
conclusion was that the cause was never missing knowledge — it was that the
operating manual had no section on the subject. The equivalent systemic cause
is named for each bug below. One of them is uncomfortable, and it goes first.

---

## The headline — a documented failure shape recurred, hours after being re-read

Finding #2 of the 2026-08-23 audit was a `fetch` whose failure fell through to
the success path: the client never checked `res.ok`, so a failed order cleared
the cart and rendered "Order confirmed". It is written up in the RCA, in
`CLAUDE.md` §0, and in the security agent's own checklist.

On 2026-08-26 at 23:50 (`290085f`), the nightly reconciliation route shipped
with this line around its alert email:

```ts
}).catch(() => {});
```

`fetch` rejects **only on network failure**. A revoked `RESEND_API_KEY` returns
HTTP 401, which *resolves* the promise — the catch never fires, the route
answers 200, and the one message that must not be missed rings into a void.
The exact shape of finding #2, in new code, written by the same process that
had read the RCA describing it, **the same day it wrote three other fixes
citing that RCA**. Eight minutes later the security-agent review of the route
caught it, and `3908db2` fixed it before the schedule ever ran.

Two conclusions, and the second matters more than the first:

1. **Prose does not prevent recurrence.** Reading an RCA does not stop hands
   from typing the idiom. `.catch(() => {})` around a `fetch` is muscle memory
   from a hundred codebases where the request was optional. Knowledge written
   down is necessary and *demonstrably not sufficient*.
2. **The review step is what worked.** The 2026-08-23 RCA's process fix was
   "security review is a written step with an owner, invoked before route
   changes ship". That step fired here and converted a live recurrence into an
   eight-minute one. The lesson is not "try harder to remember" — it is that
   the only reliable form of a rule is one that is *executed*: a mandatory
   review pass, a test that goes red, a helper that makes the wrong thing
   unwritable. Every proposed fix at the end of this file is held to that
   standard.

The worst property of this instance: the failing component **was the alarm**.
A silent failure anywhere else is eventually noticed by its consequences. A
silently failing alert removes the control you believe you have while leaving
every dashboard green — strictly worse than never building it.

## Bug 1 — the save endpoint wrote five empty columns and said "Saved"

**What happened.** `/api/account/measurements` read `{bust, waist, hip,
height, notes}`. The "Save my measurements" button posts the flattened string
a cart line carries: `{measurements: "Bust / chest: 90cm, Waist: 74cm, …"}`.
The body matched nothing; `boundedText(undefined, …)` produced five empty
values; the upsert wrote them; the route answered `{ok: true}`; the button
rendered "Saved. Next time these are filled in for you." Nothing was saved.
For a signed-in customer this also **overwrote** previously saved numbers with
blanks — silent data loss dressed as success.

**Why it was possible.** This is the 2026-08-23 root cause 1 wearing different
clothes. That RCA: *a handler written for one caller was extended and the
input handling wasn't revisited.* Here the mirror image: **a new caller was
added to an existing handler and the handler's contract was never checked.**
`d64ee65` built the button around the value it had in hand (the flattened
string) and assumed the route would take it. The route, written nine days
earlier for the `/account` form, had no reason to expect a second shape — and
crucially, it was *permissive*: a body containing none of its known fields was
not an error, just a row of empties.

**Why it wasn't caught.** Three independent reasons, each sufficient:
- The button itself was invisible (an underlined sentence nobody clicked), so
  the path had **zero production executions** until `818f8bc` made it a
  button. A capture prompt nobody can see captures nothing — and *tests*
  nothing.
- The success message was derived from the HTTP response, and the HTTP
  response was derived from "the upsert did not throw" — not from "the data
  the customer typed is now in the columns". Every layer truthfully reported
  its own happy path.
- Nothing anywhere asserted the caller's actual payload against the route's
  actual parser. Client and route were each verified alone.

**The fix (`426484b`).** The route now tries the flattened shape first via
`parseMeasurements` — the same parser the tailor's tech pack uses, so there is
no second format to keep in step — and falls back to the field shape.
`scripts/test-measurements.mjs` now runs **both callers' real payloads**
through the same column-derivation the route uses and asserts every field
survives. Re-run while writing this RCA: green.

**The rule, stated so it generalises:**
- *Adding a caller to a route is the same event as extending a route: the
  contract must be re-audited from both ends.* The 08-23 rule triggered on
  "the handler changed". It must also trigger on "who calls it changed".
- *A write endpoint that recognises nothing in the body must refuse.* If the
  route had returned 400 when no known field was present, this bug would have
  surfaced on the first click as a visible error instead of a false "Saved".
  Strict parsing is a safety property, not pedantry.

## Bug 2 — an environment variable navigated the customer away and the data died

**What happened.** The signed-out flow held the typed measurements in a React
ref, opened Clerk's sign-up modal, and posted after Clerk reported a session.
But Amplify sets `NEXT_PUBLIC_CLERK_SIGN_UP_FORCE_REDIRECT_URL=/account`, so
completing sign-up **navigated the customer off the design page**. The ref
died with the unmount; the POST never happened; the customer landed on
`/account` with an empty measurements form, having just typed their numbers
one page ago.

**Why it was possible.** The env var was set in the console for a different
flow (the standalone `/sign-up` page) and left no git trace — root cause 3 of
the previous RCA, again. It is an **ambient parameter**: `clerk.openSignUp({})`
looks self-contained in the source, but its post-signup behaviour is decided
by deployment configuration the code never mentions. The component's comment
even said "Clerk's modal, not a redirect: leaving the page mid-design would
lose everything" — the intent was written down at the call site and the
environment silently overrode it.

**Why it wasn't caught.** Locally the env var isn't set, so dev behaved as
intended. The failure existed only in the deployed environment, only for
signed-out users, only after completing a sign-up — and the sign-up itself
*succeeded*, so every observable signal (account created, landed on the
account page) read as normal.

**The fix (`426484b`).** `openSignUp` now passes `forceRedirectUrl:
window.location.href` explicitly, which Clerk documents as taking precedence
over the env var — verified in a browser: `Clerk.buildAfterSignUpUrl()`
returned `/account` while standing on `/size-guide` before the fix. Belt and
braces: the pending value is also stashed in sessionStorage and drained on
`/account` too, so the save lands wherever the flow ends up.

**The rule:** *a global default configured for one flow is an invisible
argument to every other flow.* Any call whose behaviour an environment
variable can change (Clerk redirects above all) passes its intent explicitly
at the call site. Note the standing hazard: the env var is **still set** in
the console (verified below, and it is needed by the standalone sign-up page)
— so every future `openSignUp`/`openSignIn` call that omits `forceRedirectUrl`
reintroduces this bug on the spot.

## Bug 3 — one person's body measurements written onto the next person's account

**What happened.** The first version of the sessionStorage stash (built inside
the same session to fix bug 2) had no expiry and was cleared only after a
*successful* save. An abandoned sign-up therefore left person A's body
measurements parked in the tab. On a shared browser — family iPad, showroom
device, internet café — the drain-on-session effect would fire for **whoever
signed in next**, and person A's measurements would be written onto person B's
account, over B's own saved numbers. PII disclosure (B reads A's bust/waist/hip
on their account page) and data destruction (B's numbers overwritten) in one
move, with `{ok: true}` at every step.

**Why it was possible.** The stash was reasoned about as "my measurements
crossing my sign-up" — a single-user mental model of a browser. sessionStorage
is scoped to the tab, not to the person; anything that survives in it across
an auth boundary and later *authorizes or drives a write* as
whoever-is-signed-in is a cross-customer channel. This is the previous RCA's
"one imagined caller" failure transplanted into the client: one imagined
*user*.

**Why it wasn't caught — actually, it was.** This is the one that worked. The
security review of `426484b` ran before shipping, asked the adversarial
question ("who else can be holding this tab?"), and the fix went into the same
commit. It is listed here because the founder asked for all five and because
the *pattern* — pre-auth data applied post-auth to an unverified identity —
will recur in any "save this for later" feature (saved addresses are on the
open list).

**The fix (`426484b`).** A 15-minute TTL (`PENDING_TTL_MS` in
`src/lib/measurements.ts`), written as `{value, ts}` and refused if expired,
unparseable, or timestamped in the future (a moved-back clock is not trusted);
plus clear-on-load-when-signed-out — a signed-out mount with nothing pending
in the ref means any stashed value belongs to an abandoned sign-up, and it is
dropped rather than adopted. All of it asserted in
`scripts/test-measurements.mjs`, including "expired entry is deleted, not
re-offered".

**The rule:** *data captured before authentication and applied after it must
either be bound to the identity that created it or expire fast — and must be
cleared the moment the flow it belongs to is known to be over.* Browser
storage is a surface shared between customers, not an extension of one
customer's memory.

## Bug 4 — the alarm's own failure path was `.catch(() => {})`

Covered as the headline above. The mechanics, for completeness:

**What happened.** The reconciliation route's alert email was
`fetch("https://api.resend.com/emails", …).catch(() => {})`. Any HTTP-level
failure — 401 from a revoked key, 403, 422, 500 — resolves the promise, skips
the catch, and the route returns 200. EventBridge sees only the status code,
so its retry and failed-invocation metric never move. Every way the alert
could fail was a way nobody would hear about.

**Why it was possible.** `fetch`'s API design (reject on network error only)
plus an idiom — "this request is best-effort, don't let it break the route" —
imported from contexts where the request *was* optional. Here the request was
the route's entire purpose.

**Why it wasn't caught at write time.** With a valid key the happy path works
perfectly, and the failure condition (a revoked key, an empty `STAFF_EMAILS`)
is precisely a condition no casual test produces. Absences are invisible to
happy-path testing — root cause 4 of the previous RCA, verbatim.

**The fix (`3908db2`).** `res.ok` checked; a failed send (or an empty
`STAFF_EMAILS`, or an unset `RESEND_API_KEY` with problems found) logs a
status code — no PII — and returns **500**, so EventBridge retries and its
metric moves. A scheduler only ever sees the status code, so a failed send has
to be a failed request.

**The rule:** *a resolved `fetch` is not a successful `fetch`; `res.ok` is
part of making the request, everywhere, server-side included.* And its
corollary: *an alerting path may never swallow its own failure — it must
convert it into the loudest signal its caller can perceive* (here: a non-2xx
status). `.catch(() => {})` around anything that alerts, persists, or pays is
wrong in every case.

## Bug 5 — the token was set in the console and undefined in production

**What happened.** Amplify's build spec writes the runtime env file with an
explicit allowlist: `env | grep -e DATABASE_URL -e STRIPE_SECRET_KEY … >>
.env.production`. `RECONCILE_TOKEN` was set in the console but absent from the
grep, so `process.env.RECONCILE_TOKEN` was `undefined` in the running app
while the console showed it configured. The route — by its own deliberate
design — returns 404 when the token is unset, so a request with the *correct*
token got "Not found". An hour went to the deploy queue, CloudFront header
stripping, and re-checking the token value before anyone read the build spec.

**Why it was possible.** Two sources of truth for one fact ("which env vars
exist at runtime"), one of them — the allowlist — effectively invisible: it
lives in the build spec, changes in the console, and leaves no git trace. The
2026-08-23 RCA's root cause 3 ("credential state lives outside the repo, so
docs go stale silently") named the console as the thing to verify. This bug is
one level deeper: **the console itself was the stale layer.** Verifying "is it
set in Amplify?" — the exact check the last RCA prescribed — returns *yes*
while production sees nothing.

**Why it wasn't caught quickly.** The route's 404-when-unconfigured is a sound
security choice (an unconfigured deployment must not advertise an admin
endpoint) with an unpriced cost: it collapses "not configured", "wrong path"
and "not deployed" into one indistinguishable signal, **for the operator as
much as for an attacker**. The debugging trusted the console as ground truth
for runtime env, and the deceptive-by-design response pointed everywhere
except the true layer.

**The fix.** `-e RECONCILE_TOKEN` added to the build-spec grep in the console
and redeployed (no git trace — verified directly below), and the trap written
into `CLAUDE.md` by `fdc403a`: a new env var takes **two steps**, console and
build spec, and the spec is read at build time so it needs a redeploy.

**The rule:** *the console showing a variable set is not evidence the process
sees it — the only ground truth for runtime configuration is the running
process's behaviour.* And: *when a route deliberately hides its unconfigured
state from outsiders, write down where its configuration lives at the point
of definition* — the reconcile route's comments now do — *because you will one
day debug it with exactly the information an attacker has.*

## What the five have in common

The founder's read: four of five failed silently and reported success. After
reading all five diffs — agreed on the four:

1. `{ok:true}` + "Saved" over five empty columns.
2. A completed, apparently successful sign-up, with the data quietly gone.
3. A successful save — of the wrong person's measurements onto the wrong
   account (latent; never fired).
4. HTTP 200 from a route whose alert had failed.

Bug 5 is the honest disagreement, and it sharpens the lesson rather than
weakening it: it did **not** fail silently — it failed loudly and *lied about
which layer had failed*. A 404 against a correct token, with the console
swearing the token was configured. So the common factor across all five is not
silence. It is that **the system's self-report was wrong**: four reported
success where there was failure; the fifth reported the wrong failure. In
every case the report was generated from something *other than the thing it
claimed* — "the request returned", "the upsert didn't throw", "the sign-up
completed", "the console shows it set" — never from the effect itself.

That is this RCA's version of the previous one's "the manual had no section on
security": the operating manual (§7, and the whole verify-before-you-claim
culture) is about *the session* not claiming success without checking. Nothing
in it said *the product* must not claim success without checking. Every one of
these bugs is a success signal — a UI message, a 200, a `{ok:true}`, a console
tick — derived from a proxy. The check that catches this class is always the
same and always end-to-end: **observe the effect, not the report.** Click the
real button, then read the real columns. Trigger the alert with a broken key,
then look for the 500. Curl the deployed route, then believe the response over
the console.

And the headline stands over all of it: one of these five was a *documented*
failure shape recurring in fresh code hours after the documentation was
re-read. Written rules decay on contact with habit. Rules that held were the
executed ones — the security review that caught bugs 3 and 4 before they
shipped, and the test file that now holds bugs 1 and 3 shut. Prefer that form
for every rule this file produces.

## Proposed additions to CLAUDE.md §0 (for founder review — not applied)

In the style of the existing non-negotiables:

- **A resolved `fetch` is not a success.** `fetch` rejects only on network
  failure; a 401 or 500 *resolves*. Every `fetch` — client or server — checks
  `res.ok`, and `.catch(() => {})` is banned around anything that alerts,
  persists, or pays. An alert path converts its own failure into a non-2xx so
  the scheduler's retry and metrics fire. (2026-08-23 finding #2; **recurred
  2026-08-26** in `290085f`, caught by review in `3908db2`.)
- **A write route that recognises nothing must refuse.** If none of a
  handler's known fields are present in the body, return 400 — never write
  defaults and answer `{ok:true}`. And adding a **new caller** to an existing
  route is the same event as extending the route: re-audit the contract from
  both ends, and put the caller's real payload through the route's real parser
  in a test (`scripts/test-measurements.mjs` is the pattern).
- **A success message is derived from the effect, not the request.** The UI
  may say "Saved" only on a response that confirms what was actually written.
  Verifying the feature means clicking the real control and reading the real
  row.
- **Clerk redirect env vars are ambient arguments.**
  `NEXT_PUBLIC_CLERK_SIGN_UP_FORCE_REDIRECT_URL=/account` is set in the
  console and stays (the standalone `/sign-up` page needs it). Therefore every
  `openSignUp`/`openSignIn` call **must** pass `forceRedirectUrl` explicitly,
  or a completed sign-up navigates the customer to `/account` and any
  in-progress page state dies.
- **Pre-auth data applied post-auth must expire.** Anything stashed in
  browser storage before sign-in and consumed after it gets a short TTL and is
  cleared whenever a signed-out state is observed — on a shared browser the
  tab is a channel between customers, and measurements are PII.
- *(Already added by `fdc403a`, keep it:)* a new env var takes two steps —
  console **and** the build-spec grep allowlist — plus a redeploy. The console
  showing a variable set is not evidence the running process sees it.
