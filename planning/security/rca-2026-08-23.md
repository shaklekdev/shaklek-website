# RCA — the 2026-08-23 security audit

**What happened:** an external black-box audit of the live site found four
Critical/High issues, the worst of which let anyone buy an AED 450 garment for
AED 5 against live cards. A follow-up source-level audit found nine more.

Every finding is archived in this directory. This file is the *why*. It exists
so the same class of failure does not recur, and so the Shaklek agents
(`.claude/agents/`) start every session already knowing it.

## Root cause 1 — a trust boundary moved and the input handling didn't

This is the cause of findings #1, #2 and #3 together. It is one bug, not three.

When `/api/orders` was written, `items[].price` and `total` were **display
data**. They were untrusted, but harmlessly so: the worst outcome of a bad
value was a wrong number in an email that a person read and sanity-checked.
Nothing enforced them because nothing needed to.

`edbe6e9` moved that same field across a trust boundary — into `unit_amount`,
i.e. into what a customer's card is charged — by *extending the existing
handler* rather than writing a new one. The field's meaning changed completely.
The code that read it did not change at all.

The same commit did the same thing to the other two findings:

- **#2** — the client's `handlePay()` had no `res.ok` check because, before
  Stripe, the route had no meaningful failure mode. Stripe added 400/409/502
  paths. The client was never revisited, so a failed order cleared the cart and
  rendered "Order confirmed".
- **#3** — `/api/orders/:id` was written for exactly one caller: the
  confirmation page, immediately after a Stripe redirect. The assumption "only
  the person who just paid holds this ID" was true *for that caller* and was
  never written down, never enforced, and never re-examined once the ID started
  travelling in a shareable URL.

**The lesson, stated so it generalises:** when a value starts being used for
something new — especially money, identity, or authorization — re-audit every
place it enters the system. Extending a handler is not a small change; it is a
new threat model for every field the handler already read.

**How to catch it next time:** for any endpoint that touches payment or PII,
write down which request fields are authoritative and which are advisory. If a
field is advisory, the server must recompute it. `src/lib/pricing.ts` is that
rule made executable.

## Root cause 2 — the project's written process had no security in it

This is the systemic one, and it is the reason the gaps went unnoticed for nine
days across many sessions.

`CLAUDE.md` is this project's operating manual, and it is a *good* one. Its
§7 "How to work here — the expensive lessons" is detailed, specific and
hard-won. But every lesson in it is derived from image-generation failures:
token cost, scope creep, verifying a recolour with the right instrument, not
deleting generated images. The word "security" does not appear.

Sessions optimise for what is written down. What was written down was: don't
waste generation budget, don't exceed the ask, verify before claiming. Those
were followed. Application security was never on the list, so it was never
checked — not once, across the entire build of a payment flow.

**The fix is not "try harder".** It is that security review is now a written
step with an owner: `.claude/agents/shaklek-security.md`, invoked before any
change to payments, auth, or a route handler ships.

## Root cause 3 — credential state lives outside the repo, so docs go stale silently

`CLAUDE.md` claimed Stripe was on test keys. It was written at ~20:00 on
2026-08-22; the keys were swapped in the **Amplify console** after that. A
console change leaves no git trace, so nothing contradicted the doc and nothing
prompted an update.

This directly worsened the severity of finding #1: the price hole was assessed
as "test mode, no real money" when it was in fact charging live cards.

**Rule:** the repo must never be the source of truth for credential *state*.
Verify it, don't read it:

```bash
# Which Stripe mode is production actually in?
aws amplify get-app --app-id dqcptedylrif0 --query 'app.environmentVariables' --output json
# Which Clerk instance is live? (publishable key is public by design)
curl -s https://www.shaklek.com/ | grep -oE 'pk_(live|test)_[A-Za-z0-9]+'
```

Both were run on 2026-08-23. Stripe: live. Clerk: `pk_live_`, domain
`clerk.shaklek.com` — so `CLAUDE.md` was stale on *both* credential claims, and
the Clerk MAU-cap outage it warned about no longer applies.

## Root cause 4 — "verified working" was scoped to the happy path

The external audit's own "Verified working" section is instructive: webhook
signature verification, route protection, no secret leakage, TLS. All correct.
All things that were *built deliberately* and therefore *tested deliberately*.

Every finding was in something nobody decided to build: no one decided not to
validate prices; no one decided to omit `res.ok`. They were absences, and
absences are invisible to happy-path testing.

**Lesson:** testing that a feature works cannot find a missing control. Only an
adversarial pass — "what would I attack here?" — finds absences. That is
exactly what the security agent is for, and why its prompt is written to look
for what is *missing*, not to review what is present.

## What was actually fixed (2026-08-23)

All verified against a production build by probing, not by reading code.

| Finding | Fix | Proof |
|---|---|---|
| #1 client-controlled price | `src/lib/pricing.ts` recomputes from catalog by slug | `{price:5,name:"FREE",category:"Dress"}` → `Oversized Shirt / Shirt / 390` |
| #2 false "Order confirmed" | `res.ok` + `data.ok` checked before clearing; error surfaced | 409 renders an error, cart intact |
| #3 no authz on order read | HMAC token from `success_url`, or Clerk session owning it | no token → 404; non-uuid → 404, not 500 |
| #4 no security headers | `next.config.ts` headers + CSP + `poweredByHeader:false` | all present on `/`, `x-powered-by` gone |
| open redirect (new) | `Origin` allowlisted before use in `success_url` | cross-origin POST → 403 |
| webhook not idempotent (new) | gated on `pending_payment → paid` transition | replay updates 0 rows, skips emails |
| email HTML injection (new) | `esc()` on every interpolated field | — |
| unverified-email authz (new) | `getVerifiedEmail()` requires `verification.status === "verified"` | — |
| `/api/trends/*` public (new) | `STAFF_EMAILS` allowlist | → 401 |
| no rate limiting (new) | `/api/orders` 10/10min, `/api/customize` 60/min | — |
| unbounded bodies (new) | `rejectOversizedBody` on every write route | — |
| CSRF (new) | `rejectCrossOrigin` on state-changing routes | — |
| cart localStorage (new) | try/catch write, validated read | — |

**Known accepted risk:** the CSP keeps `'unsafe-inline'` on `script-src`.
Removing it requires nonces via `proxy.ts`, which forces dynamic rendering
across the catalog. Documented in `next.config.ts`; revisit if an XSS sink
is ever introduced.

**Not verified:** no browser was available to check the CSP for console
violations. Origins were verified statically against the built bundles and
against Clerk's own shipped `content-security-policy.js`.
