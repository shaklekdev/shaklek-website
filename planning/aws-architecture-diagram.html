Shaklek — Technical Architecture

The full AWS picture, before we build another piece of it

Every service the product needs, how they connect, and — just as important — which ones are actually AWS versus third-party APIs that happen to be called from AWS. The AI layer is a real part of this, not a footnote: two distinct flows (live customization, weekly trend intake) that both call the same external Google Gemini API, not an AWS service.

Why Gemini is external, and why that's an acceptable trade-off: AI used to live inside the AWS boundary via Amazon Bedrock — Claude for text, Nova Canvas for images, both on the AWS bill. That changed: Nano Banana's specific strength is consistent, targeted image edits — change one thing on a garment photo, keep everything else identical — which is a better technical fit for live customization previews than Nova Canvas was, and running text + image through one external vendor is simpler than splitting AI across two providers (AWS and Google). The cost is real: Gemini doesn't share AWS's bill or IAM, it's its own account, its own outage surface, same as Clerk and Stripe already are. Gemini, Clerk, payment, and Resend are now the full list of external dependencies AWS-hosted code calls — none of them show up on the AWS bill, and an AWS outage doesn't take any of them down, but a Gemini, Clerk, Resend, or Stripe outage isn't something AWS support can fix either.

Auth, payment, and AI: decided

All three were open at some point in this doc's history. The same constraint settled all of them: this gets maintained by one person, so the option with the least ongoing operational surface won even where a "more AWS-native" or technically-purer option existed.

DecisionChosenPassed over
Auth Clerk — fully managed: prebuilt sign-in UI, session handling, and magic-link/social login all done for you. Free tier (~10k MAU) covers pilot scale, so "cheapest" and "easiest" agree here. Cognito stays inside AWS but has real, well-documented friction for custom flows. Auth.js is free but self-hosted — you own the session logic and DB adapter yourself. Both cost more in maintenance time than Clerk, even though Clerk is the paid option on paper.
Payment gateway Stripe — best documentation and developer experience by a wide margin. Stripe Checkout is a hosted page, so Shaklek's code never touches card details (near-zero PCI burden). Settles in AED, operates in the UAE directly. Telr / PayTabs are UAE-local and may integrate more natively with some local banks and bundle Tabby/Tamara BNPL — but cost more integration and maintenance effort without a clear offsetting advantage at pilot scale. Tabby still gets added as a separate direct integration later; Stripe doesn't block it.
AI (text + image) Google Gemini API (Nano Banana) — one external vendor for both text parsing and image generation. Nano Banana's specific strength is consistent, targeted image edits: change one detail on a garment photo, keep everything else identical — a closer technical fit for the live customization preview than Nova Canvas. See pricing below. Amazon Bedrock (Claude + Nova Canvas) stayed inside AWS's bill/IAM but split image quality was the weaker fit, and it was itself a correction from an earlier, now-outdated Titan Image Generator reference. Direct Anthropic API was never image-capable at all — ruled out from the start, same reasoning as the original Bedrock decision.

What Gemini actually costs

Researched 12 August 2026 against Google's published rates and AI Studio — worth re-checking directly before it becomes a real line item, AI pricing moves fast and this wasn't verified against a live console.

Model / tierFree tierPaid rate
Nano Banana (base) ~500 images/day free in AI Studio ~$0.039–0.05 per 1024×1024 image, pay-per-request, no commitment
Nano Banana Pro None — not in the free tier at all $0.134 per image at 1K/2K resolution, $0.24 at 4K
Google AI subscription — ~$20/month flat, higher limits — a recurring commitment regardless of usage, worse fit than pay-per-request for pilot-stage, spiky usage
Recommendation: pay-per-request, base Nano Banana, not the Pro tier or the monthly subscription — at pilot volume (a handful of previews and one weekly trend batch), the free tier likely covers most usage, and paid overage stays in single-digit dollars, not a recurring bill. This still needs one open item resolved: confirm in the actual codebase which tier (base vs. Pro) is being called — they're priced completely differently, and "Nano Banana" alone doesn't specify which.

How a request actually flows, step by step

The boxes above show what talks to what. This is what happens, in order, inside each of the two flows — deliberately detailed enough to show exactly which steps are real code today and which are still a sketch.

A — Customer designs and checks out synchronous, seconds

  1. built Browser requests shaklek.com → DNS resolves to AWS Amplify → Amplify serves the pre-rendered catalog page (src/app/page.tsx) from its CDN edge cache.
  2. built Customer opens a catalog item → /design/[slug], statically generated per item at build time from src/data/catalog.ts via generateStaticParams().
  3. not built Customer types a customization request (or taps Quick Customize) → browser POSTs to a new Amplify API route, e.g. /api/customize. Today, Quick Customize just cycles a hardcoded local color list — no network call at all.
  4. not built That route calls the Google Gemini API (Nano Banana) to parse the free-text request into the structured design-spec schema (garment id, requested changes, notes), and to run the hard constraint checks: one fabric, one layer, no logos, and the originality-distance rule against any brand reference.
  5. not built If the spec passes, the same route calls Nano Banana again for image generation — image-to-image, conditioned on the base item's photo pulled from S3 plus the structured spec — producing a constrained preview. Never generated from a blank canvas; that's what keeps the preview close to something a tailor could actually cut, and it's specifically what Nano Banana is strong at: a targeted edit that keeps everything else about the photo identical.
  6. not built If the spec fails a constraint check instead, no preview is generated — the request routes to a human stylist by email, exactly like today's Phase 1 flow (/api/custom-requests). The AI only ever adds a preview on top of that; it doesn't replace the human fallback.
  7. not built The preview image is written to S3; its URL and the structured spec return to the browser and render next to the catalog photo.
  8. built Customer proceeds to /checkout → fills in size, color, notes → total computed client-side from src/data/colors.ts pricing rules.
  9. not built Checkout submits to Stripe Checkout (hosted payment page) instead of today's payment-method picker UI, which currently has no gateway behind it.
  10. not built Stripe redirects back on success; a Stripe webhook hits an Amplify API route to confirm the payment and write the order to Amazon RDS as a durable record — today, an order only ever exists as an email.
  11. built /api/orders emails orders@shaklek.com via Resend with the order details (needs RESEND_API_KEY to actually send today — currently just logs).

B — Weekly trend intake scheduled, asynchronous

  1. not built Amazon EventBridge fires on a weekly schedule (e.g. Monday, early hours Gulf time), invoking an AWS Lambda trend-intake function.
  2. not built Lambda pulls trend signals from configured sources — recurring silhouettes, colors, construction details — explicitly not full images or listings. This is the concrete mechanism behind the "not scraping and reproducing" rule in dossier §11, not just a policy statement.
  3. not built Lambda calls the Google Gemini API (Nano Banana) to turn the aggregated signals into a short list of candidate concepts: title, garment type, a description of the pattern being chased, source count, weeks running — the same shape already modeled in src/data/trends.ts.
  4. not built For each candidate, Lambda calls Nano Banana again — image-to-image, conditioned on a same-category base catalog photo from S3 — to produce an inspired, non-copied preview image, stored back to S3.
  5. not built Lambda writes each candidate to Amazon RDS with status = pending. Never directly into the live catalog table — this is the row that makes the human-review step non-optional rather than a suggestion.
  6. built A stylist opens /dashboard/trends (real UI, ships today) — sees each candidate's preview, signal description, source count, and weeks-running, and clicks Approve or Reject. Currently runs entirely on the mock data in src/data/trends.ts; nothing persists on reload yet.
  7. not built Approve should write status = approved back to RDS and copy the candidate into the live catalog table, making it purchasable. Reject should mark it rejected and stop there. Today, both actions only update local component state in the browser.
  8. not built The dashboard itself needs Clerk-based staff auth in front of it — right now /dashboard/trends is a public URL with no login at all.
