Every service the product needs, how they connect, and — just as important — which ones are actually AWS versus third-party APIs that happen to be called from AWS. This now includes the AI layer as a real part of the architecture, not a footnote: it's actually two distinct flows with different AWS services behind them, not one box.

Why Bedrock lives inside the AWS boundary and Anthropic doesn't: Calling Anthropic's API directly would mean a third-party dependency outside AWS entirely — its own bill, its own outage surface, no shared IAM. Amazon Bedrock hosts the same Claude models (plus Titan Image Generator, which Anthropic doesn't offer) as a first-party AWS service, so it shows up on the one AWS bill, inherits the same IAM permissions as everything else in the diagram, and needed a separate box at all only because it's genuinely a different capability — reasoning versus image generation — not because it's a different vendor. Clerk, payment, and Resend are the real external dependencies: third-party products that AWS-hosted code happens to call over the internet, don't show up on the AWS bill, and an AWS outage doesn't take them down — but a Clerk, Resend, or Stripe outage isn't something AWS support can fix either.

Auth and payment: decided

Both were open as of the last revision of this doc. One constraint settled both: this gets maintained by one person, so the option with the least ongoing operational surface won even where a "more AWS-native" or "more local" option existed.

DecisionChosenPassed over
Auth Clerk — fully managed: prebuilt sign-in UI, session handling, and magic-link/social login all done for you. Free tier (~10k MAU) covers pilot scale, so "cheapest" and "easiest" agree here. Cognito stays inside AWS but has real, well-documented friction for custom flows. Auth.js is free but self-hosted — you own the session logic and DB adapter yourself. Both cost more in maintenance time than Clerk, even though Clerk is the paid option on paper.
Payment gateway Stripe — best documentation and developer experience by a wide margin. Stripe Checkout is a hosted page, so Shaklek's code never touches card details (near-zero PCI burden). Settles in AED, operates in the UAE directly. Telr / PayTabs are UAE-local and may integrate more natively with some local banks and bundle Tabby/Tamara BNPL — but cost more integration and maintenance effort without a clear offsetting advantage at pilot scale. Tabby still gets added as a separate direct integration later; Stripe doesn't block it.

How a request actually flows, step by step

The boxes above show what talks to what. This is what happens, in order, inside each of the two flows — deliberately detailed enough to show exactly which steps are real code today and which are still a sketch.

A — Customer designs and checks out synchronous, seconds

  1. built Browser requests shaklek.com → DNS resolves to AWS Amplify → Amplify serves the pre-rendered catalog page (src/app/page.tsx) from its CDN edge cache.
  2. built Customer opens a catalog item → /design/[slug], statically generated per item at build time from src/data/catalog.ts via generateStaticParams().
  3. not built Customer types a customization request (or taps Quick Customize) → browser POSTs to a new Amplify API route, e.g. /api/customize. Today, Quick Customize just cycles a hardcoded local color list — no network call at all.
  4. not built That route calls Claude on Bedrock to parse the free-text request into the structured design-spec schema (garment id, requested changes, notes), and to run the hard constraint checks: one fabric, one layer, no logos, and the originality-distance rule against any brand reference.
  5. not built If the spec passes, the same route calls Titan Image Generator on Bedrock — image-to-image, conditioned on the base item's photo pulled from S3 plus the structured spec — producing a constrained preview. Never generated from a blank canvas; that's what keeps the preview close to something a tailor could actually cut.
  6. not built If the spec fails a constraint check instead, no preview is generated — the request routes to a human stylist by email, exactly like today's Phase 1 flow (/api/custom-requests). The AI only ever adds a preview on top of that; it doesn't replace the human fallback.
  7. not built The preview image is written to S3; its URL and the structured spec return to the browser and render next to the catalog photo.
  8. built Customer proceeds to /checkout → fills in size, color, notes → total computed client-side from src/data/colors.ts pricing rules.
  9. not built Checkout submits to Stripe Checkout (hosted payment page) instead of today's payment-method picker UI, which currently has no gateway behind it.
  10. not built Stripe redirects back on success; a Stripe webhook hits an Amplify API route to confirm the payment and write the order to Amazon RDS as a durable record — today, an order only ever exists as an email.
  11. built /api/orders emails orders@shaklek.com via Resend with the order details (needs RESEND_API_KEY to actually send today — currently just logs).

B — Weekly trend intake scheduled, asynchronous

  1. not built Amazon EventBridge fires on a weekly schedule (e.g. Monday, early hours Gulf time), invoking an AWS Lambda trend-intake function.
  2. not built Lambda pulls trend signals from configured sources — recurring silhouettes, colors, construction details — explicitly not full images or listings. This is the concrete mechanism behind the "not scraping and reproducing" rule in dossier §11, not just a policy statement.
  3. not built Lambda calls Claude on Bedrock to turn the aggregated signals into a short list of candidate concepts: title, garment type, a description of the pattern being chased, source count, weeks running — the same shape already modeled in src/data/trends.ts.
  4. not built For each candidate, Lambda calls Titan Image Generator on Bedrock — image-to-image, conditioned on a same-category base catalog photo from S3 — to produce an inspired, non-copied preview image, stored back to S3.
  5. not built Lambda writes each candidate to Amazon RDS with status = pending. Never directly into the live catalog table — this is the row that makes the human-review step non-optional rather than a suggestion.
  6. built A stylist opens /dashboard/trends (real UI, ships today) — sees each candidate's preview, signal description, source count, and weeks-running, and clicks Approve or Reject. Currently runs entirely on the mock data in src/data/trends.ts; nothing persists on reload yet.
  7. not built Approve should write status = approved back to RDS and copy the candidate into the live catalog table, making it purchasable. Reject should mark it rejected and stop there. Today, both actions only update local component state in the browser.
  8. not built The dashboard itself needs Clerk-based staff auth in front of it — right now /dashboard/trends is a public URL with no login at all.
