How Shaklek actually runs, now that it is running

This document used to describe a plan. The site has been live and taking real card payments since 22 August 2026, so it now describes what is deployed. Everything marked live below was verified against the running system on the date in the footer, not recalled from the plan.

Three things the earlier version of this page got wrong, corrected rather than quietly patched. It named Amazon RDS as the database — the database is Neon Postgres, which is not an AWS service. It showed Amazon S3 holding files — no S3 bucket exists; catalog photography is committed to the repository and served by Amplify. And it drew Google Gemini in the request path, called live during a customer session — Gemini is never called at runtime. It is a build-time tool on a developer's laptop. AWS is a smaller part of this system than the old title claimed: Amplify is the only AWS service in it.

The failure mode nothing was watching for. An order is only marked paid, and only gets its shipping address, when Stripe's webhook reaches us. Stripe retries a failing webhook for about three days and then stops. If it never lands, the customer has been charged and our database still says pending_payment with nowhere to ship to — money taken, order invisible. CloudWatch cannot see this: the site is perfectly healthy, it is the data that is wrong.

scripts/reconcile-orders.mjs now checks every order against Stripe and reports any payment without a complete, shippable order. It is read-only and prints ids only. Run it after any incident touching the webhook, and periodically regardless.

How a purchase actually flows

  1. live Browser loads www.shaklek.com → Amplify serves the pre-rendered home page and catalogue from its CDN edge.
  2. live The customer opens a piece, moves the sliders, and the preview swaps to a real photograph of that exact combination — no generation, just a lookup keyed by comboKeyForCategory().
  3. live They choose Tailored and type their measurements, or pick a standard size. Fields turn green inside the accepted range and print the range underneath.
  4. live Add to cart (a browser-local cart), then /checkout. A promotion code, if entered, is validated by /api/promo/validate for display only — it never sets the real discount.
  5. live POST /api/orders. Every price is recomputed from catalog.ts here; the client's total is only a mismatch check, and the fabric is pinned to something we can actually cut. A pending order row is written to Neon and a Stripe Checkout session is created.
  6. live The customer pays on Stripe's hosted page. Shaklek's code never sees a card number.
  7. live Stripe's webhook calls /api/webhooks/stripe. Signature verified, state transition gated (Stripe delivers at-least-once), the true paid total written back over the pre-discount figure, and Resend emails the stylist. This, not the browser redirect, is what makes an order real.
  8. live The customer lands on /order-confirmed. Staff open /dashboard/orders and download a tech pack PDF for the tailor, built by src/lib/techPack.ts from the order row plus the technical flat for that exact combination.
  9. live The loop closes after delivery. A QR on the thank-you card in the parcel opens /fit. She answers five questions about how the piece actually sat and POST /api/fit-feedback appends a row to fit_feedback, attached to her most recent paid order. On her next order that row prints on the tailor's tech pack. She can see every entry, and delete them, from /account.

The one unauthenticated write, and why it is shaped the way it is

/api/fit-feedback is the only route on the site that writes to a customer record without a login. That is deliberate — it is reached by a QR on a printed card, by a woman holding a garment, and a password wall there collects nothing. Two security reviews shaped what follows; the second was run because the first had reviewed code that a redesign had already replaced.

  • rule It answers every request identically — same body, same status, same headers, whether the email is a paying customer, a stranger or nonsense. A route that 404s on an unknown address is a customer-list oracle: feed it emails and it tells you who shops here.
  • rule It is one SQL statement, always. Not for elegance: branching on whether the customer exists rebuilt that same oracle out of latency — one database round trip for a stranger, three for a real customer, with byte-identical responses. Found by review. Do not turn this back into a lookup plus a conditional write.
  • rule Nothing is ever overwritten. Founder's instruction. A row per submission, each naming the order it was about, because a body changes and three entries a year apart mean something one cannot.
  • rule It matches on lower(email). Guest checkout stores an address exactly as typed, so a case-sensitive match silently saved nothing for anyone who typed a capital — invisible, because the response is identical either way.
  • rule Capped at 100 rows per customer, inside that same statement. Append-only plus an unauthenticated writer plus an unbounded account-page read is a way to make a customer's own account fail to load.
  • accepted Someone who knows a customer's email can add a false entry. They cannot read anything back and cannot destroy a real one. The tech pack caption says explicitly that the note is unverified and does not replace the measurements. The real fix, if it is ever needed, is a signed per-order link printed as variable data.

Where the images live, and how they reach a customer

The founder's question, answered by measuring production rather than reading the code. Short version: there is no image host. Every photograph is a file in the git repository.

  1. live Stored in the repo at website/public/catalog/ — 463 files, 38 MB across nine garment folders plus flats/, and public/marketing/ (4 files, 3.1 MB). No S3 bucket, no CDN origin, no database. They are committed, so they travel with the deploy and are versioned like code.
  2. live Referenced by src/data/catalog.ts, the single source of truth. npm run build runs verify-catalog.mjs first and exits non-zero if any referenced file is missing — a broken path used to build green and deploy broken images.
  3. live Served through Next's image optimizer (/_next/image?url=…&w=…&q=…) running on Amplify. It resizes to the width the layout asks for and converts to WebP for clients that accept it.
  4. live Cached by CloudFront for four hours, keyed by the full URL. Measured on production: catalog images are 23–35 KB WebP and return x-cache: Hit from cloudfront.
Fixed 2026-08-27: 290 files were named .png and contained JPEG data. The optimizer picks its output format from the extension, not the file's magic bytes, so every one of them was re-encoded as PNG for any client that does not accept WebP. Measured on the same garment at the same width, before and after the rename:

no-WebP client: 167,304 B → 29,822 B (image/png → image/jpeg). WebP clients were already fine and are unchanged at ~18 KB.

286 garment photos plus 4 marketing images renamed with git mv; 145 references updated across catalog.ts, seo.ts, Hero, Concept and /our-story. The 64 files in flats/ were left alone — they are genuinely PNG, which is the right format for line art, and flats.ts constructs their names with a .png suffix.

⚠️ This was never the cause of the perceived lag, and was not done to fix it — modern browsers accept WebP and always got the small file. It matters for older iOS and in-app webviews. Any future rename uses .jpg.

Why the repo and not S3. It costs nothing, versions with the code, and cannot drift from catalog.ts. The limit is Amplify's 230 MB build-output cap: at 38 MB of catalog inside an 89 MB output there is real headroom, but it grows with every item × colour × combination. Moving to S3 + CloudFront is on the list for that reason and for retiring the filename cache-busting rule — not for speed. Images are not the slow part; that was measured.

Deploying, and the three traps that have bitten

Both cost a day each in August 2026. Neither is obvious from a green build.

  1. trap Amplify rejects a build output over 230MB. The catalogue is the bulk of it, so catalog images are stored as JPEG q92. Shipping them as PNG once produced a 291MB output and a failed deploy.
  2. trap Replacing an image in place changes nothing for visitors. Photos are served through Next's optimizer and CloudFront caches that response for four hours, keyed by URL — and Amplify owns the distribution, so there is no invalidation available. Changed content means a changed filename. That is what the -v2/-v3 suffixes are for.
  3. trap Amplify never runs a database migration, and drizzle-kit migrate does not work here either. The build spec is npm ci then npm run build; there is no migrate step and never has been. Worse, the documented fallback lies: this schema was created with drizzle-kit push, so drizzle.__drizzle_migrations is empty — the tool believes every migration since 0000 is unapplied, tries to create tables that already exist, and exits 0 having done nothing. It did exactly that twice on 2026-08-28. Apply the generated SQL yourself in a transaction, then verify against information_schema, never against the exit code. Migrate first, push second.
  4. note A failed build is silent — the site keeps serving the previous version. When a change is not live, check the job status before blaming caching.

Security posture

An external audit on 23 August 2026 found that anyone could buy an AED 450 garment for AED 5 against live cards, plus three more Critical/High issues; a follow-up source audit found nine more. The full record and root-cause analysis is in planning/security/rca-2026-08-23.md.

The rule that would have prevented all of it: when a value starts being used for something new — money, identity, authorization — re-audit every place it enters the system. /api/orders was written when items[].price was harmless display data for an email. Stripe was later bolted onto the same handler, turning that same untrusted field into unit_amount. The trust boundary moved; the input handling did not.

P2 — worth doing, not urgent

  1. approved Stripe → Meta Conversions API. The browser pixel misses conversions — ad blockers, iOS tracking prevention, a customer closing the tab before the confirmation page renders. Sending the purchase from the server instead does not miss them, so Meta optimises against real sales. The caution is only about where the code goes: the only place that knows a payment truly succeeded is /api/webhooks/stripe, which is the same handler the AED 5 vulnerability lived in. So it gets a security review, not a quick patch.
  2. approved if cheap Rate limiting that survives more than one container. Today's counters live in Lambda container memory and reset on a cold start. Upstash Redis free tier (10k commands/day) covers this at no cost; AWS WAF would be ~$8/month and is overkill. No abuse has appeared, so this is insurance, not a fire.
  3. cheap, do it opportunistically Catalog images to S3 + CloudFront. Not a latency fix — see the callout above. The real arguments are that it removes the 230MB build-output cap (463 files, 38MB today, growing with every item × colour × combination) and retires the filename cache-busting rule, because an object store can be invalidated and a build cannot. Cost at this scale is pennies: 38MB of storage is under $0.01/month.

P3 — later, by decision

  1. deferred Customer order-status emails. Founder's call, and the reasoning is sound: large brands go quiet between purchase and shipping too. Revisit if "where is my order" mail starts arriving.
  2. deferred Tabby / Tamara. Not yet.
  3. check, don't build Neon backups. Neon does point-in-time recovery on its own, so this is likely already working — confirm the retention window and restore one into a branch once. Orders are the only irreplaceable data here.
  4. check, don't build Resend domain authentication (SPF / DKIM / DMARC). These are DNS records that prove shaklek.com really sent the mail. Without them Gmail and Outlook may file the order confirmation as spam — and a customer who pays and then sees no email cannot tell the difference between "it went to spam" and "my order failed". That produces support mail, repeat orders, and chargebacks. Checking takes minutes.
  5. tidy-up /upload is live but linked from nowhere — and it is in sitemap.ts at priority 0.8, so search engines can send people to it. Its uploaded reference photo is never persisted, so a paid order from that page reaches the tailor as a boolean. Since it is not a funnel the founder is running, the cheap fix is removing it from the sitemap rather than building object storage for it. Reinstate properly if uploads ever become a real feature.
